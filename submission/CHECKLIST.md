# HackPSU submission checklist

Prepared on October 25, 2026. This file is a handoff checklist, not evidence that submission occurred.

## Event requirements

Source: user-supplied Hacker's Guide Fall '26, registration/submission page and FNB/Nittany AI pages; [Devpost overview](https://hackpsu-fall-2026.devpost.com/) and [rules](https://hackpsu-fall-2026.devpost.com/rules).

- The guide asks for a Devpost draft by midnight Sunday. If one does not already exist, create it promptly and ask the Info Booth how the draft-creation rule applies; do not assume an exception.
- Devpost's Requirements text specifies **noon Sunday, October 25** as the hard submission cutoff for table assignment. Edits may continue until **1:45 PM**. The page header displays **2 PM**, so follow the earlier requirements text rather than relying on that header.
- Submit on **both** devpost.hackpsu.org **and** hackpsu.org/profile → Submit Project.
- One project per team, with every teammate included; teams have at most five members.
- Final hacking/edits end at 1:45 PM. The Expo is 2–3:30 PM, ECoRE second floor, with the whole team at the table for judges.
- Prepare a two-minute pitch. Judging covers impact, creativity, quality, and technical complexity.
- Confirm all contributors are eligible/registered, the project was built during the permitted event window and on the premises, original work and sources are accurately disclosed, and the project was not submitted to another competition. Do not assert these facts on someone else's behalf without confirmation.

## Product gate before recording or making live claims

- [ ] Restart the backend from the current source, rebuild/reload extension v0.2.0, and reload the public product tab.
- [ ] Open Service connection & setup → Check service setup. Backend should report v0.2.0. Presence of a key is not proof that it is valid.
- [ ] Keep REVIEW_ANALYSIS_MODE=local for the default key-free review check. No GPTZero payment or key is required. Never paste any credentials into Devpost, screenshots, Git, or this checklist.
- [ ] Run the diagnostics command on the actual test merchant from a network-enabled terminal. Inspect source statuses and limitations.
- [ ] Test toolbar → side panel → extraction → /analyze → displayed findings in Chrome on the actual demo product.
- [ ] Test a tab change mid-scan, retry/force-refresh, unavailable provider, and backend downtime.
- [ ] Capture one successful source-supported live result, if available. Otherwise label the demo fictional and disclose the remaining live-verification limitation.
- [ ] Verify all four fictional scenarios. Never present fixture merchants or evidence as real.
- [ ] Check long titles and source excerpts at 380 and 420 px; keyboard focus and the result announcement must work.
